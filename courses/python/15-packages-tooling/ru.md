## 15.1 Сторонние пакеты и PyPI

**PyPI** (Python Package Index, <https://pypi.org>) — официальный «магазин приложений» Python, в нём больше шестисот тысяч бесплатных пакетов. Некоторые из самых популярных:

| Пакет | Назначение |
|-------|-----------|
| `requests`, `httpx` | работа с сайтами и веб-API |
| `numpy`, `pandas` | вычисления, анализ табличных данных |
| `matplotlib` | графики и диаграммы |
| `fastapi`, `flask`, `django` | сайты и веб-сервисы |
| `pillow` | обработка изображений |
| `rich` | цветной красивый текст и таблицы в терминале |
| `pytest` | тестирование |
| `torch`, `transformers` | глубокое обучение и большие модели (см. учебник по LLM в этом проекте) |

После установки ими пользуются так же, как стандартной библиотекой, — просто `import`:

```python norun
# сначала установите в терминале: uv add requests (или pip install requests)
import requests

r = requests.get("https://api.github.com")
print(r.status_code)          # 200 означает успех
print(r.json()["current_user_url"])
```

## 15.2 Виртуальные окружения: свой «набор инструментов» для каждого проекта

Если ставить все пакеты в системный Python, проблемы начнутся быстро: проекту A нужна версия пакета 1.0, а проекту B — 2.0, и они конфликтуют; к тому же непонятно, от каких пакетов на самом деле зависит каждый проект.

**Виртуальное окружение** (virtual environment) даёт каждому проекту **свою папку** (обычно `.venv`), куда устанавливаются пакеты этого проекта, и проекты не мешают друг другу.

Со встроенными в Python `venv` и `pip`:

```bash
$ python -m venv .venv                 # создать виртуальное окружение в текущей папке
$ source .venv/bin/activate            # активировать (macOS / Linux)
$ .venv\Scripts\activate               # активировать (Windows)
(.venv) $ pip install requests         # после активации pip ставит пакеты только в это окружение
(.venv) $ pip freeze > requirements.txt   # записать список зависимостей
(.venv) $ deactivate                   # выйти из виртуального окружения
```

Пока окружение активно, в начале строки приглашения видно `(.venv)`.

## 15.3 uv: современный инструмент «всё в одном»

**uv** (от компании Astral, написан на Rust) объединяет «установку Python, создание виртуальных окружений, установку пакетов, фиксацию версий и запуск программ» в одном инструменте и работает в 10–100 раз быстрее pip. Для многих новых проектов он стал первым выбором, и этот курс тоже его рекомендует (как установить — в уроке 4 вводного курса).

```bash
$ uv init my-app             # создать новый проект (с pyproject.toml, README и др.)
$ cd my-app
$ uv add requests rich       # добавить зависимости: создаёт .venv, ставит пакеты, записывает в pyproject.toml и uv.lock
$ uv add --dev pytest ruff   # инструменты только для разработки (тесты, проверка кода)
$ uv run main.py             # запустить программу в окружении проекта (без ручной активации)
$ uv run pytest              # запустить тесты
$ uv remove rich             # удалить зависимость
$ uv python install 3.13     # установить нужную версию Python
$ uv sync                    # на другом компьютере: воссоздать точно такое же окружение по uv.lock
```

Плюсы: **не нужно вручную активировать окружение** (`uv run` сам использует окружение проекта), а `uv.lock` записывает **точную версию** каждого пакета, так что кто угодно (и вы через год) получит идентичное окружение командой `uv sync`.

### `pyproject.toml`: «паспорт» проекта

`pyproject.toml`, который создаёт `uv init`, — стандартный файл настроек проектов на Python. Выглядит он примерно так:

```toml
[project]
name = "my-app"
version = "0.1.0"
description = "Мой первый проект"
readme = "README.md"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.32",
    "rich>=14.0",
]

[dependency-groups]
dev = ["pytest>=8", "ruff>=0.12"]

[tool.ruff]
line-length = 100
```

`>=2.32` в `dependencies` означает «2.32 или новее». Номера версий обычно имеют вид `основная.дополнительная.исправление` (**семантическое версионирование**): новое «исправление» только чинит ошибки; новая «дополнительная» версия добавляет возможности, а старый код продолжает работать; новая «основная» версия может содержать несовместимые изменения.

### Типичная структура проекта

```text
my-app/
├── pyproject.toml        настройки проекта и зависимости
├── uv.lock               точно зафиксированные версии (ими управляет uv, не правьте вручную)
├── README.md             описание проекта
├── .gitignore            говорит Git не сохранять .venv, __pycache__ и т. п.
├── src/
│   └── my_app/
│       ├── __init__.py   с этим файлом папка становится «пакетом»
│       └── core.py
└── tests/
    └── test_core.py      код тестов
```

В `.gitignore` должны быть как минимум `.venv/` и `__pycache__/`: виртуальное окружение всегда можно воссоздать через `uv sync`, поэтому сохранять его в Git не нужно и не следует (урок 7 вводного курса).

## 15.4 ruff: стиль кода и статические проверки

У сообщества Python есть руководство по стилю — **PEP 8**: отступ 4 пробела, имена переменных в стиле `snake_case` (строчные буквы с подчёркиваниями), имена классов — `CamelCase`, пробелы вокруг операторов… Единый стиль делает чужой код таким же приятным для чтения, как свой.

**ruff** (тоже от Astral) **автоматически** делает две вещи:

```bash
$ uv run ruff format .       # форматирование: переписывает код в едином стиле
$ uv run ruff check .        # проверка: находит вероятные ошибки и плохие приёмы
$ uv run ruff check --fix .  # исправляет то, что можно исправить автоматически
```

Например, для такого кода:

```python norun
import os, sys
def Add(a,b):
    unused = 1
    if a == None:
        return b
    return a+b
```

`ruff check` укажет, что в одной строке импортировано несколько модулей, что `os` и `sys` импортированы, но не используются, что переменная `unused` присвоена, но не используется, и что `== None` следует писать как `is None`; `ruff format` расставит недостающие пробелы и пустые строки. (Имя функции `Add` нарушает правила именования PEP 8; эта проверка работает, только если в настройках включены правила `N`.)

> [!TIP]
> Установите расширение **Ruff** в VS Code — файлы будут форматироваться при сохранении, а проблемы подсвечиваться прямо в редакторе.

## 15.5 Проверка типов: ловим ошибки до запуска

Как говорилось в уроке 10, Python не проверяет аннотации типов. **Инструмент проверки типов** читает ваш код и аннотации и находит ошибки типов, **не запуская программу**:

```python norun
def total_price(prices: list[float]) -> float:
    return sum(prices)

print(total_price(["3.5", "2"]))      # передаётся список строк
```

```bash
$ uv run mypy main.py
main.py:4: error: List item 0 has incompatible type "str"; expected "float"
```

Распространённые инструменты: **mypy**, **pyright** (встроен в расширение Pylance для VS Code) и более новый **ty** от Astral. Чем больше проект, тем полезнее проверка типов.

## 15.6 Автоматические тесты: pytest

Написав функцию, вы вручную пробуете несколько примеров. **Автоматические тесты** превращают эти примеры в код, и после любого изменения одной командой можно проверить их все — убедиться, что вы не сломали то, что работало.

**pytest** — самый популярный инструмент тестирования, и он очень прост: файлы с именами на `test_`, функции с именами на `test_` и `assert` внутри:

```python norun
# файл src/my_app/core.py
def slugify(title: str) -> str:
    """Превращает заголовок в вид для адреса страницы: строчные буквы, пробелы → дефисы."""
    return "-".join(title.lower().split())
```

```python norun
# файл tests/test_core.py
from my_app.core import slugify

def test_basic():
    assert slugify("Hello World") == "hello-world"

def test_extra_spaces():
    assert slugify("  Learn   Python  ") == "learn-python"

def test_empty():
    assert slugify("") == ""
```

```bash
$ uv run pytest
============================= test session starts ==============================
collected 3 items

tests/test_core.py ...                                                   [100%]

============================== 3 passed in 0.01s ===============================
```

Каждая точка `.` — пройденный тест. Если тест не прошёл, pytest ясно показывает, «что ожидалось и что получилось на самом деле».

Учебная программа и сайт запускают по одному файлу, поэтому pytest там напрямую не использовать. Встроенный модуль **unittest** позволяет попробовать ту же идею в одном файле:

```python
import unittest

def slugify(title: str) -> str:
    return "-".join(title.lower().split())

class TestSlugify(unittest.TestCase):
    def test_basic(self):
        self.assertEqual(slugify("Hello World"), "hello-world")

    def test_extra_spaces(self):
        self.assertEqual(slugify("  Learn   Python  "), "learn-python")

    def test_empty(self):
        self.assertEqual(slugify(""), "")

unittest.main(argv=["tests"], exit=False, verbosity=2)    # результаты выводятся в поток ошибок (stderr)
```

> [!NOTE]
> Распространён и подход **«сначала тесты»** (разработка через тестирование, TDD): сначала пишутся тесты «как функция должна работать», вы видите, что они падают, затем пишете код, пока они не пройдут. Автоматическая проверка каждого задания на программирование в этом курсе — это, по сути, набор тестов.

## 15.7 Отладка: `breakpoint()` и `logging`

Есть способы отладки лучше, чем расставлять `print` повсюду:

**1. Точки останова**: напишите в коде `breakpoint()`, и программа остановится там в отладчике `pdb`, где можно смотреть переменные и выполнять код по строке:

```python norun
def average(nums):
    total = sum(nums)
    breakpoint()            # остановка здесь; p total — показать переменную, n — следующая строка, c — продолжить, q — выйти
    return total / len(nums)
```

В редакторах VS Code и PyCharm есть графические отладчики: щёлкните слева от номера строки, чтобы поставить точку останова, и нажмите F5 — гораздо нагляднее.

**2. Журналирование**: модуль `logging` лучше `print` подходит для записи того, что делает программа: у сообщений есть уровни (отладка, информация, предупреждение, ошибка) и время, а в рабочем режиме отладочные сообщения отключаются одной настройкой:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
log = logging.getLogger("shop")

def buy(item, money):
    log.debug("собираюсь купить %s", item)    # уровень INFO, поэтому сообщения DEBUG скрыты
    if money < 10:
        log.warning("не хватает денег на %s: всего %d руб.", item, money)
        return False
    log.info("куплено: %s", item)
    return True

buy("книга", 30)
buy("игрушка", 5)
```

## 15.8 Итоги

- Сторонние пакеты лежат на PyPI; ставьте их через `uv add имя` или `pip install имя`, затем `import`.
- **Одно виртуальное окружение на проект** (`.venv`) избавляет от конфликтов версий; не сохраняйте `.venv` в Git.
- **uv**: `uv init` создаёт проект, `uv add` добавляет зависимости, `uv run` запускает код, `uv sync` восстанавливает окружение; зависимости записаны в `pyproject.toml`, точные версии зафиксированы в `uv.lock`.
- **ruff format** поддерживает единый стиль (PEP 8), **ruff check** находит проблемы; **mypy / pyright / ty** проверяют типы.
- **pytest**: файлы и функции на `test_` + `assert`; `uv run pytest` запускает все тесты разом.
- Отлаживайте через `breakpoint()` или отладчик редактора; записывайте ход работы через `logging`.

Прочитайте строку с двумя номерами версий (например, `1.10.0 1.9.3`) и выведите **более новую** или `equal`, если они одинаковы. Пример вывода: 1.10.0

- чтобы Python работал быстрее
